Баг-репорт для редактора vc.ru и спецификация для плагина Obsidian «Копировать как ...»

Ниже собраны два готовых рабочих материала: структурированный баг-репорт с минимальными патчами для команды «Комитета» (vc.ru / DTF) и полная техническая спецификация клиентского редактора vc.ru, на базе которой можно построить плагин для Obsidian с контекстным подменю «Копировать как ...» и адаптерами под vc.ru, Дзен и Смартлаб. Вторая версия юзерскрипта из прошлого шага с высокой вероятностью не сработала по одной из двух причин: либо в той же вкладке остался активным первый перехватчик paste (его stopImmediatePropagation() перехватывал событие раньше, а повторно отправленное событие с isTrusted === false второй скрипт игнорировал), либо в буфере присутствовал непустой text/html, из-за чего редактор полностью игнорировал исправленный text/plain.

Разбор клиентского бандла index-7X-HR7JT.js и чанка Editor-BDsWKcso.js показывает, что поломка копипаста на Windows вызвана не отказом от внутреннего формата, а сочетанием четырёх конкретных дефектов в модуле вставки Voe, инструменте заголовков Sb и санитайзере Xoe. Ключевой инженерный вывод для будущего плагина Obsidian: в Windows браузер Chromium системно добавляет возврат каретки \r\n при чтении text/plain, поэтому адаптеру vc.ru надёжнее обходить сломанную ветку text/plain через обнаруженный в appendHTMLParts «мост» в text/html — оборачивать блоки формата [tool:{...}] в одиночные теги <p> с JSON-экранированием внутренних тегов (\u003c, \u003e). Этот механизм выведен непосредственно из кода бандла и требует короткой живой проверки в консоли vc.ru перед реализацией плагина.

Проверка каталога Obsidian Community Plugins, GitHub и Хабра показала, что готового плагина с контекстным подменю и адаптерами для vc.ru, Дзена и Смартлаба сейчас нет — ниша для площадок Рунета свободна. При этом существует близкий по архитектуре open-source прототип Pubcopy (лицензия MIT, адаптеры для Medium и Substack через подменю ПКМ), который удобно использовать как архитектурный референс или базу для форка.

Готовый баг-репорт и минимальные патчи для команды vc.ru / DTF

Материал ниже оформлен так, чтобы его можно было без переработки отправить команде «Комитета» или опубликовать в разделе багов. В отчёт включены все четыре подтверждённых дефекта в порядке убывания критичности.

Текст баг-репорта

Заголовок: Редактор (CodeX Editor / Paragraph): на Windows сломана многоблочная вставка text/plain (включая копирование между черновиками), теряется уровень H3, а одиночные блоки и инлайн-форматирование в HTML отбрасываются

Окружение: веб-редактор vc.ru / DTF (общий движок редактора в клиентских бандлах index-7X-HR7JT.js и Editor-BDsWKcso.js); Windows 10/11 + Chromium-браузеры (Chrome, Edge, Яндекс Браузер). На macOS баг № 1 не воспроизводится из-за системных переводов строки LF (\n), баги № 2–4 воспроизводятся на всех ОС.

Проблема 1 (Критичная): поломка многоблочной вставки text/plain на Windows из-за CRLF (\r\n)

Для воспроизведения достаточно выполнить три шага:

  1. Открыть черновик vc.ru с несколькими блоками (заголовок, абзац, список, цитата, разделитель, медиа).
  2. Выделить блоки и скопировать (Ctrl+C). Метод koe.copyToClipBoard сериализует их в text/plain через "\n\n" (заголовки в ##/###, остальные блоки в [type:{...}]).
  3. Перейти в другой черновик на Windows, поставить курсор в пустой текстовый блок (text) и нажать Ctrl+V.

Фактический результат: все блоки склеиваются в один текстовый блок в виде сырого текста (### Заголовок, [list:{"items":...}], [media:{...}]).

Причина в коде (Voe.prototype.preparePlain): метод режет входной текст строго по Unix-переводам \n\n и удаляет только \n:

preparePlain(t) {
  return t.split("\n\n").filter(s => s.trim().length > 0).map(s => Uoe(s, "\n"));
}

На Windows системный буфер обмена и Chromium возвращают clipboardData.getData("text/plain") с переводами строк \r\n (CRLF). Разделитель между блоками превращается в \r\n\r\n, внутри которого нет подстроки \n\n. В результате t.split("\n\n") возвращает массив длиной 1 со всем текстом целиком. Затем appendPlainParts(t) проверяет t.length === 1 и отправляет весь текст в defaultPasteBehaviour("", t[0]) в обход парсера appendPlainPart.

Минимальный патч:

preparePlain(t) {
  return t
    .replace(/\r\n?/g, "\n")
    .split("\n\n")
    .filter(s => s.trim().length > 0)
    .map(s => Uoe(s, "\n"));
}

Проблема 2 (Высокая): при копировании и вставке подзаголовки H3 деградируют в H2

При копировании блока header со стилем h3 вместе с любым вторым блоком и последующей вставке обратно (на macOS или на Windows после исправления CRLF) подзаголовок всегда превращается в h2, хотя при копировании koe.copyToClipBoard корректно формирует "### Текст".

Причина в коде (Sb.markdown.parseFrom): сериализация parseTo учитывает уровень заголовка ("#".repeat(n) + " " + s.text), но обратный парсер parseFrom срезает все # без подсчёта их количества, жёстко возвращает style: "h2" и оставляет ведущий пробел перед текстом:

// Текущий код в Sb:
parseFrom(s) {
  for (; s.charAt(0) === "#"; ) s = s.substring(1);
  return { text: s, style: "h2" };
}

Минимальный патч:

parseFrom(s) {
  const match = s.match(/^(#+)\s+(.*)$/);
  if (!match) return { text: s.trim(), style: "h2" };
  return {
    text: match[2],
    style: match[1].length >= 3 ? "h3" : "h2"
  };
}

Проблема 3 (Средняя): одиночный блок в text/plain обходит парсер Markdown и [tool:{...}]

Если скопировать и вставить в пустой текстовый блок ровно один блок (например, список [list:{...}], цитату [quote:{...}] или [header:{"text":"...","style":"h3"}]), строка вставляется как сырой текст без создания соответствующего блока.

Причина в коде (Voe.prototype.appendPlainParts): условие t.length === 1 безусловно перенаправляет одиночный элемент в defaultPasteBehaviour("", t[0]), не вызывая appendPlainPart.

Минимальный патч: проверять одиночный блок на совпадение с сериализованным тегом или Markdown-паттерном, сохраняя возврат Promise:

appendPlainParts(t) {
  if (t.length === 1) {
    const single = t[0];
    const isStructured =
      /^\[([a-zA-Z]+):(.+)\]$/.test(single) ||
      Boolean(this.editor.toolsManager.matchMarkdown(single));
    if (isStructured && this.editor.blocks.currentBlock.isEmpty) {
      const r = this.appendPlainPart(single);
      if (r) this.editor.caret.setToBlock(r, this.editor.caret.positions.END);
    } else {
      this.defaultPasteBehaviour("", single);
    }
    return Promise.resolve();
  }
  return t.reduce((s, n, i) => s.then(() => {
    const o = i === t.length - 1;
    const r = this.appendPlainPart(n);
    if (o && r) this.editor.caret.setToBlock(r, this.editor.caret.positions.END);
  }), Promise.resolve());
}

Проблема 4 (Улучшение UX): санитайзер HTML при вставке вырезает <b>, <i>, <br> и <mark>

Базовый конфиг санитайзера Xoe.DEFAULT разрешает только теги p и a, тогда как сам инструмент текста (nl.prototype.sanitize) при сохранении поддерживает a, b, i, p, mark и br. В результате при копировании форматированного текста из Google Docs, Notion или Obsidian через text/html всё строковое выделение и переносы <br> удаляются ещё в prepareHTML и appendHTMLParts до создания блоков. Для исправления достаточно расширить разрешённые теги в prepareHTML / Xoe.DEFAULT тегами b, strong, i, em, mark, br (с нормализацией strong → b и em → i).

Техническая спецификация редактора vc.ru / DTF (CodeX Editor / Paragraph)

Редактор vc.ru и DTF представляет собой проприетарный форк блочного редактора CodeX Editor / Editor.js (внутреннее имя компонента-обёртки — Paragraph). Ядро редактора, санитайзер Xoe (на базе HTMLJanitor) и обработчик буфера Voe загружаются в основном клиентском бандле index-7X-HR7JT.js, а часть прикладных инструментов (quote, list, code, delimiter, osnovaEmbed, audio) вынесена в отдельный чанк Editor-BDsWKcso.js. Базовым блоком по умолчанию (initialBlockPlugin) в компоненте Paragraph назначен "text" (в ядре Eoe дефолтное значение — "paragraph").

Маршрутизация события paste в классе Voe (ядро CodeX Editor на vc.ru). Красным отмечены четыре бага продакшен-сборки, из-за которых ломается стандартная вставка из Obsidian на Windows. Зелёным выделен обходной HTML-мост: передача блоков формата [tool:{...}] внутри одиночных тегов <p> в text/html обходит баг Windows CRLF и санитайзер Xoe.DEFAULT.

Источники: продакшен-бандл редактора vc.ru (index-7X-HR7JT.js), Chromium Issue Tracker (#40873740).

Последовательность обработки события paste в Voe.blockPasteCallback(t) проходит через шесть последовательных стадий:

  1. Фильтр нативных полей ввода: если Xo(t.target) возвращает true (фокус в INPUT или TEXTAREA) либо активный блок currentBlock отсутствует, обработчик завершает работу без вмешательства.
  2. Приоритет файлов (Files): вызывается t.preventDefault(). Если clipboardData.types содержит "Files", управление передаётся в processFiles(i.files). Редактор сопоставляет MIME-тип с handledFiles (инструменты медиа ra и hl принимают image/png, image/jpeg, image/heic, image/webp, image/gif, video/mp4, video/quicktime, а hl дополнительно video/webm), добавляет медиаблок, передаёт файл в onPaste({ file }) и удаляет исходный пустой блок.
  3. Кастомный перехватчик блока: из буфера извлекаются a = getData("text/html") и l = getData("text/plain"). Если у текущего инструмента задан externalConfig.pasteCallback, вызывается он; возврат false прерывает дальнейшую обработку.
  4. Проверка области редактирования и развилка по типу блока: обработчик требует, чтобы цель находилась внутри [contenteditable="true"] и хотя бы одна из строк (a или l) была непустой. Далее срабатывает ключевое условие: только если currentBlock.type === "text" (initialBlockPlugin), вызывается splitAndPaste(a, l) (с последующим удалением исходного блока, если s.isEmpty). Если курсор находится в любом другом блоке (header, list, quote, code), многоблочный разбор отключается и вызывается defaultPasteBehaviour(a, l), что, например, внутри header схлопывает все переносы в одну строку.
  5. Проверка renderOnPaste внутри splitAndPaste: при непустом plain.trim() и наличии статического флага allowRenderOnPaste = true (установлен на текстовом инструменте ru) вызывается analyze(plain). Этот путь рассчитан на автопреобразование одиночных URL (ссылок, видео, соцсетей) по массиву patterns и мгновенно отклоняет любой текст длиннее 350 символов (MAX_LENGTH_TO_PARSE = 350) или содержащий хотя бы один пробельный символ (/\s/.test(plain)).
  6. Выбор между text/html и text/plain: если html (text/html) непустой, редактор безусловно запускает appendHTMLParts(prepareHTML(html)), полностью игнорируя содержимое text/plain. Ветка appendPlainParts(preparePlain(plain)) выполняется только при пустом text/html.

Механика копирования и формат text/plain

При копировании выделенных блоков внутри редактора вызывается koe.copyToClipBoard(blocks). Для каждого блока выполняется editor.saver.saveBlock(n), после чего движок проверяет наличие у блока статического свойства markdown (Wy) с методом parseTo. У текстового инструмента ru метод parseTo разворачивает внешний одиночный <p> и отдаёт innerHTML (сохраняя <br>, <b>, <i>, <a>), а у заголовка Sb формирует Markdown-строку "#".repeat(level) + " " + s.text. Все остальные инструменты (list, quote, delimiter, code, media и др.) не определяют parseTo и сериализуются в строку [${n.type}:${JSON.stringify(i.data)}]. Блоки склеиваются через "\n\n" и записываются функцией _oe(str) через скрытый <textarea> и document.execCommand("copy"), поэтому в буфер попадает исключительно text/plain.

При обратной вставке в appendPlainPart(i) каждый непустой фрагмент проходит три ступени распознавания:

  1. Вызов toolsManager.matchMarkdown(i), который вырезает zero-width пробелы \u200B и проверяет зарегистрированные регулярные выражения. В клиентском бандле такой паттерн задан у Sb (/^#+\s+\S/), но из-за Бага № 2 он всегда возвращает style: "h2".
  2. Проверка регулярным выражением /\[([a-zA-Z]+):(.+)\]/: извлекается имя инструмента a[1] и парсится JSON.parse(a[2]) как объект data. Из-за паттерна [a-zA-Z]+ инструменты с подчёркиванием или цифрами в имени (например, telegram_button) этим способом не распознаются, а сам JSON должен располагаться в одной строке (переносы внутри строк кода обязаны быть экранированы как \n). Поскольку .+ жадный, квадратные скобки внутри текста JSON-полей не ломают разбор, пока строка заканчивается на ].
  3. Фолбэк: при отсутствии совпадений создаётся блок type: "text" с { text: i }. Если же в теге [tool:{...}] передано имя незарегистрированного инструмента, обращение this.editor.toolsManager.available[s].class без проверки выбросит TypeError (хотя при рендеринге сохранённых данных getToolByType подставляет заглушку np с надписью "Блок '<name>' не поддерживается").

Механика ветки text/html и санитайзер HTMLJanitor

При наличии text/html в буфере данные проходят по цепочке prepareHTML(t) → iA(n, true) → appendHTMLParts(children). На первом шаге prepareHTML берёт копию дефолтного конфига санитайзера Xoe.DEFAULT ({ tags: { p: {}, a: { href: true, target: "_blank", rel: "nofollow" } } }), добавляет теги из handledTags доступных инструментов (H1–H6 из Sb и UL/OL/LI из oa) с предикатом checkSanitizerForBlockTags и прогоняет HTML через встроенный HTMLJanitor (Yoe).

Предикат checkSanitizerForBlockTags отклоняет CODE и IMG, если у них не задан инлайновый стиль display: block — а поскольку у медиаинструментов ra и hl вообще нет свойства handledTags (только handleFiles), любые <img> при вставке HTML отбрасываются. На этапе Xoe.clean(t, s, true) удаляются все теги вне белого списка (их текстовые потомки выносятся наружу, а SCRIPT/STYLE удаляются целиком), чистятся атрибуты, &nbsp; заменяется на пробел, вырезаются \u200B, а любые последовательности пробелов и переводов строки \s+ схлопываются в одиночный пробел. Именно здесь безвозвратно теряются <b>, <strong>, <i>, <em>, <br>, <mark> и <s>.

Затем функция iA(n, true) преобразует плоский HTML в коллекцию верхнеуровневых блочных элементов (DIV, P, H1–H6, CODE, PRE, BLOCKQUOTE, UL, OL, LI), превращая DIV в P и оборачивая свободные строчные узлы в P. Далее appendHTMLParts обрабатывает каждый непустой элемент:

  • Если коллекция состоит ровно из одного <p>, она сбрасывается в defaultPasteBehaviour.
  • Если элемент является <p> ровно с одним дочерним узлом (n.tagName.toLowerCase() === "p" && n.childNodes.length === 1), редактор декодирует базовые HTML-сущности через Hoe(n.innerHTML) (&amp;, &lt;, &gt;, &quot;, &#39;) и делегирует строку напрямую в this.appendPlainPart(...).
  • Остальные теги сопоставляются с handledTags: у Sb pasteParser возвращает { text: s.innerHTML, style: s.tagName.toLowerCase() } (благодаря чему <h3> корректно сохраняет style: "h3"), а у oa собирает <li> в массив items с type: "UL" или "OL". После этого все строковые поля повторно очищаются вызовом sanitizer.clean() с тем же Xoe.DEFAULT (снова вырезая <b>/<i> внутри пунктов списка).

При последующем сохранении уже созданных блоков работает отдельный санитайзер базового класса nl.prototype.sanitize, который гораздо мягче Xoe.DEFAULT и разрешает a (href, target="_blank", rel="nofollow noreferrer noopener"), b, i, p, mark и br (при условии непустого textContent, проверяемого функцией wr).

Справочник блоков и JSON-схемы данных

Краевые случаи и «обходной мост» для адаптера vc.ru на Windows

Четыре краевых случая определяют конструкцию адаптера vc.ru для плагина Obsidian:

  1. Проблема CRLF на Windows неустранима в чистом text/plain: в Chromium на Windows зафиксирован баг #40873740 — даже если приложение записывает navigator.clipboard.writeText('a\n\nb'), при вставке в браузер clipboardData.getData('text/plain') всё равно возвращает 'a\r\n\r\nb'. Пока vc.ru не поправит preparePlain, адаптер, пишущий только text/plain, на Windows без браузерного юзерскрипта работать не будет.
  2. Стандартный text/html теряет строковую разметку и спецблоки: при передаче обычного HTML (<p><b>жирный</b></p>, <blockquote>, <hr>) санитайзер Xoe.DEFAULT вырезает <b>, <i>, <br> и <mark>, а цитаты, код и разделители не распознаются из-за отсутствия в handledTags.
  3. Обходной HTML-мост через <p> с одним текстовым потомком: из кода appendHTMLParts следует, что каждый <p> с childNodes.length === 1 передаётся в appendPlainPart(Hoe(n.innerHTML)). Если адаптер vc.ru формирует text/html из последовательности <p>[tool:{...}]</p>, заменяя все < и > внутри JSON-строк на стандартные JSON-экранирования \u003c и \u003e, то непустой text/html направляет splitAndPaste в ветку appendHTMLParts (полностью обходя preparePlain и Windows CRLF), внутри <p> нет HTML-тегов для вырезания HTMLJanitor, а JSON.parse нативно восстанавливает <b>, <i>, <br>, <a> и <mark>, создавая полноценные блоки header (включая h3), text, list, quote, delimiter и code. В text/plain при этом кладётся чистый читаемый текст на случай вставки в обычные текстовые поля. Поскольку этот обход выведен аналитически из кода Voe/Xoe/Hoe, перед написанием адаптера его необходимо проверить коротким тестом в консоли vc.ru на всех целевых типах блоков.
  4. Защита от одиночного блока (t.length === 1): при копировании ровно одного выделенного блока единственный <p> в appendHTMLParts уйдёт в defaultPasteBehaviour и вставит [header:...] как сырой текст. Для одиночного блока адаптер должен отдавать нативный HTML-тег (<h2>, <h3>, <ul>, <ol>) либо обычный <p> без JSON-обёртки.

Спецификация целевых площадок для адаптеров: vc.ru, Дзен и Смартлаб

Чтобы ядро плагина сразу проектировалось с правильными абстракциями, ниже сведены поддерживаемые форматы, ограничения и пробелы документации по всем трём целевым площадкам.

Совместимость элементов Obsidian при вставке в vc.ru, Дзен и Смартлаб

Сравнение поддержки ключевых элементов Obsidian Flavored Markdown в четырёх режимах вставки: vc.ru (text/plain) с учётом текущих багов на Windows, vc.ru (HTML-мост) через одиночные <p> с JSON-блоками, Дзен (по официальной справке редактора статей) и Смартлаб (TinyMCE / lseditor). Ячейки со статусом «Проверить» отражают отсутствие открытой документации санитайзера Смартлаба.

Источники: исходный код редактора vc.ru (бандл CodeX Editor), vcru-publisher (GitHub), Chromium (#40873740), Справка Дзена, Smart-Lab (TinyMCE / LiveStreet).

Требования адаптера для Дзена

Согласно инженерной публикации Яндекса и сторонним инструментам (MCP-dzen, ViralDzen), редактор статей Дзена и SSR-структура публикаций dzen.ru/a/{id} опираются на Draft.js. В отдельных сторонних описаниях автопостеров упоминаются также Quill и ProseMirror, а официальной спецификации обработчика clipboardData Дзен не публикует — поэтому точную реакцию текущей Дзен-студии на вложенные списки и <br> лучше перепроверить живой вставкой.

По официальной справке редактора статей Дзена, адаптер должен учитывать строгие ограничения форматов и лимитов:

  • Поддерживаемое форматирование: полужирный, курсив, зачёркнутый текст и гиперссылки (ссылки запрещены в заголовке статьи); из блоков — подзаголовки строго H2 и H3 (автоматически собирают оглавление), маркированный и нумерованный списки, цитата.
  • Отсутствующие элементы: справка Дзена не перечисляет среди доступных инструментов блоки кода, горизонтальные разделители и таблицы. Адаптеру нужна деградация: понижать H4–H6 до H3 или жирного абзаца, разворачивать таблицы в маркированные списки (по аналогии с профилем Medium в Pubcopy), преобразовывать callouts > [!note] в <blockquote> с жирным заголовком, а блоки кода — в цитату или форматированный текст.
  • Лимиты статьи: заголовок до 140 символов, текст до 100 000 знаков с пробелами, суммарно до 100 вложений (картинки/GIF от 300 px шириной и до 30 МБ с подписью до 2000 символов, галереи до 30 фото, видео и формы). Проверку длины и подсчёт вложений удобно встроить прямо в валидатор адаптера.

Требования адаптера для Смартлаба

Смартлаб исторически работает на движке LiveStreet с визуальным редактором на базе TinyMCE (в интерфейсе фигурирует панель lseditor). На открытых страницах сайта подтверждена поддержка полужирного (Ctrl+B), курсива (Ctrl+I), подчёркнутого (Ctrl+U), зачёркнутого текста, цвета шрифта, ссылок и смайлов.

В открытом доступе отсутствует официальная спецификация разрешённых HTML-тегов и правил paste_preprocess редактора Смартлаба; пользовательские публикации упоминают лишь движок LiveStreet/TinyMCE и фильтрацию атрибутов вроде id и классов. Для адаптера это означает простую тактику: генерировать чистый семантический text/html без классов, id и CSS-переменных темы Obsidian (<p>, <h2>, <h3>, <b>, <i>, <s>, <ul>, <ol>, <blockquote>, <a>), а перед фиксацией правил для таблиц, блоков кода и тега <cut> снять актуальный объект tinymce.activeEditor?.settings в DevTools на странице создания поста Смартлаба.

Архитектура плагина Obsidian «Копировать как ...»

Оптимальная база — модульный TypeScript-плагин (сборка через esbuild, стандартная структура плагинов Obsidian), разделённый на четыре независимых слоя: интеграция UI, парсер Obsidian Markdown в AST, реестр адаптеров площадок и кроссплатформенный модуль буфера обмена.

Интеграция в контекстное меню и нюансы setSubmenu()

Официальный API Obsidian позволяет встраивать пункты в контекстное меню редактора (editor-menu) и меню файла/проводника (file-menu) через this.app.workspace.on(...). В editor-menu при наличии выделения логично копировать editor.getSelection(), а при пустом выделении — всю заметку editor.getValue(); в file-menu — читать весь файл через app.vault.read(file).

Для каскадного подменю «Копировать как ...» в десктопном Obsidian (с ветки v1.4.x) существует метод MenuItem.setSubmenu(), который применяют в том числе Pubcopy и Canvas Node Align. Однако это приватный (недокументированный) API: его нет в официальном obsidian.d.ts, поэтому потребуется расширение типов (module augmentation), а при публикации в Community Plugins или запуске на мобильных устройствах жёсткая привязка к нему может не пройти ревью или не сработать.

Надёжный паттерн — feature detection с деградацией в SuggestModal выбора адаптера:

declare module 'obsidian' {
  interface MenuItem {
    setSubmenu?: () => Menu;
  }
}

this.registerEvent(
  this.app.workspace.on('editor-menu', (menu, editor, info) => {
    menu.addItem((item) => {
      item.setTitle('Копировать как ...').setIcon('copy');
      if (typeof item.setSubmenu === 'function') {
        const submenu = item.setSubmenu();
        for (const adapter of this.adapters) {
          submenu.addItem((sub) =>
            sub
              .setTitle(adapter.name)
              .setIcon(adapter.icon)
              .onClick(() => this.copyWithAdapter(adapter, editor, info))
          );
        }
      } else {
        item.onClick(() => this.openAdapterPickerModal(editor, info));
      }
    });
  })
);

Помимо контекстного меню стоит продублировать каждый адаптер отдельной командой в Command Palette (this.addCommand), чтобы пользователи могли назначать хоткеи на любимые площадки.

Кроссплатформенная запись в буфер обмена (Web Clipboard API vs Electron)

Для записи в системный буфер обмена стоит использовать стандартный Web Async Clipboard API (navigator.clipboard.write + ClipboardItem), как это делают Pubcopy и obsidian-copy-image-text. Метод работает на десктопе и мобильных клиентах, ограничивается только записью (write-only, не читает чужой буфер) и позволяет атомарно записывать text/html и text/plain раздельно или вместе:

async function writeClipboard(payload: { html?: string; plain: string }): Promise<void> {
  const items: Record<string, Blob> = {
    'text/plain': new Blob([payload.plain], { type: 'text/plain' })
  };
  if (payload.html) {
    items['text/html'] = new Blob([payload.html], { type: 'text/html' });
  }
  await navigator.clipboard.write([new ClipboardItem(items)]);
}

Если конкретному адаптеру нужно записать строго text/plain (например, для чистого Markdown), ключ text/html просто не включается в ClipboardItem.

Прямое обращение к require('electron').clipboard нежелательно сразу по четырём причинам: оно не работает на iOS/Android; в Electron 44 проведена реархитектура модуля clipboard с удалением старых методов вроде writeHTML() и availableFormats() в пользу асинхронного ClipboardItem; синхронные IPC-вызовы буфера Electron внутри асинхронных команд Command Palette в Obsidian способны провоцировать баг со сбросом состояния редактора и сдвигом frontmatter; и даже Electron API не отменяет того, что на Windows чтение text/plain в Chromium возвращает CRLF (\r\n). Поэтому связка navigator.clipboard.write() и HTML-моста (после живой проверки последнего) даёт наиболее переносимый клиентский вариант без зависимости от ОС и приватных токенов API.

Пайплайн преобразования Obsidian Markdown в AST и интерфейс адаптеров

Обработка Markdown регулярными выражениями быстро ломается на вложенных списках, блоках кода, таблицах и экранировании. Проверенный стандарт в экосистеме Obsidian (Pubcopy, Advanced Copy, Copy as PlainText, Anki AST Sync) — единый AST-конвейер на базе unified + remark-parse + remark-gfm, организованный в три этапа:

  1. Препроцессинг контекста Obsidian: удаление YAML frontmatter (--- ... ---), опциональное раскрытие встроенных заметок ![[note]] через MetadataCache и Vault, очистка комментариев %%...%%, блочных идентификаторов ^block-id и (по настройке) хештегов #tag.
  2. Построение расширенного MDAST: remark-parse + remark-gfm (таблицы, зачёркивание, списки задач), дополненные плагинами синтаксиса Obsidian — remark-obsidian-md (портирует вики-ссылки [[Page|Alias]], embeds, callouts, ==highlight==, комментарии в стандартный MDAST) и/или remark-callout (gz-remark-callout, корректно парсит форматирование внутри заголовков callout).
  3. Сериализация через изолированный адаптер (PlatformAdapter):
export interface ConvertContext {
  sourcePath: string;
  settings: PluginSettings;
  warnings: string[]; // Сборщик предупреждений для Notice (как WarningCollector в Pubcopy)
}

export interface ClipboardPayload {
  html?: string;
  plain: string;
}

export interface PlatformAdapter {
  readonly id: string;           // 'vcru' | 'dzen' | 'smartlab' | 'habr' | 'clean-md'
  readonly name: string;         // Подпись пункта в подменю «Копировать как ...»
  readonly icon: string;         // Иконка Lucide из Obsidian
  convert(ast: Root, ctx: ConvertContext): Promise<ClipboardPayload>;
}

Такое разделение позволяет один раз реализовать всю специфику Obsidian в общем ядре, а поддержку каждой новой площадки (vc.ru, Дзен, Смартлаб, Хабр, Telegram) добавлять в виде отдельного файла-адаптера, который собирает предупреждения в ctx.warnings и выводит их через new Notice(...) при потере или деградации неподдерживаемых элементов (например, о пропущенных локальных картинках или сплющенных таблицах).
